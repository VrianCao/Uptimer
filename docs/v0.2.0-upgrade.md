# Deploy and upgrade Uptimer v0.2.0

English | [中文](v0.2.0-upgrade.zh-CN.md)

**For an existing site, sync your fork, run Plan, review the target, and manually run Apply.** Sync fork brings the code into your repository. With Actions enabled, expect CI on the synced commit. Start the Cloudflare deployment from **Deploy to Cloudflare**. For supported legacy sites, the Action migrates the existing D1 database and resumes monitoring.

To have an agent check your setup or run the upgrade with your approval, copy the [upgrade prompt in the README](../README.md#upgrade-to-v020-with-an-agent).

## What v0.2.0 changes

- **Probe history and resource usage.** D1 keeps complete probe samples in time buckets and buffers writes for the current hour. The upgrade migrates existing samples and keeps the database UUID.
- **Status page loading.** The homepage displays preloaded data while checking for updates. Latency charts load on demand and respect reduced-motion settings. The main page stays usable if the chart script fails to load.
- **Public visibility and admin usability.** Monitor visibility applies to history, incidents, and maintenance. Monitor-scoped records retain their visibility restrictions when links are removed. The admin UI also improves same-origin sign-in, narrow-screen dialogs, and keyboard use.
- **Deployment review and recovery.** Plan builds the release and records the target and migrations. Apply uses the reviewed build. Rerunning an interrupted Apply skips migrations already committed to D1.

## Choose the path that fits your site

| Your situation                                              | What to do                                                                                                              |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| You have no deployed site                                   | Use **`install`**. Add two secrets and the workflow creates the resources.                                              |
| You have an existing site                                   | Use **`upgrade`** and keep the existing Worker, D1, hosting mode, and runtime profile.                                  |
| Apply stopped during maintenance or migration               | **Rerun the original Apply** with its original Plan. The workflow continues from the migrations already recorded in D1. |
| Your fork is synced and the site still runs the old version | Start at **Plan**.                                                                                                      |
| The target version is deployed and the site is healthy      | You can finish here.                                                                                                    |

**Workers + Pages** is the default hosting mode. If your existing site uses Workers Assets, select `single_worker`. The runtime profile is independent of hosting. Leave `UPTIMER_RUNTIME_PROFILE` unset for `free`, or retain `UPTIMER_RUNTIME_PROFILE=paid` if the site already uses it. Keep your current choices for this upgrade. See the [configuration reference](configuration-reference.md) and [hosting and runtime switch guidance](upgrade-and-recovery.md#runtimehosting-switches--执行路径与托管切换).

## Upgrade an existing fork

### 1. Check your fork and sync

1. Confirm that the upstream release or release candidate you intend to use has been published and that its changes are on the upstream branch you will sync. Use the guide and workflow from that version.
2. Open your fork and check the target branch. Look for custom deployment workflows, Pages Git integration, or any other setup that might deploy on push. If syncing would start one of those deployments, review and resolve that configuration through a pull request first.
3. Click **Sync fork → Update branch** on your fork. If GitHub reports a conflict, use its pull request flow to resolve it and preserve your settings. Enable Actions in your fork if needed and wait for CI on the synced commit.

Most existing sites can reuse `CLOUDFLARE_API_TOKEN` and `UPTIMER_ADMIN_TOKEN`. The admin key must match the one already used by the site. Check that custom resource names and domains still point to the existing installation. Plan can identify a unique Cloudflare account and read the D1 UUID from the live Worker’s `DB` binding.

[Uptimer releases](https://github.com/VrianCao/Uptimer/releases) · [GitHub fork sync documentation](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/syncing-a-fork) · [Secrets and configuration](deploy-github-actions.md#1-add-two-secrets)

### 2. Generate and review the Plan

In your fork, open **Actions → Deploy to Cloudflare → Run workflow**. Select the branch you checked and choose `release_action=plan` and `operation=upgrade`. Keep the current hosting mode. Choose `deploy_mode=auto` when the existing repository variable already selects the correct mode.

Open **Summary** after Plan completes.

| Check         | Expected result                                                                                             |
| ------------- | ----------------------------------------------------------------------------------------------------------- |
| Source        | The commit you intend to deploy.                                                                            |
| Target        | The existing Cloudflare account, Worker, D1 UUID, and Pages project if applicable.                          |
| Configuration | The existing hosting mode and runtime profile.                                                              |
| Migrations    | A supported `0014` upgrade lists the pending files and warns of maintenance. A current schema shows `none`. |
| Blockers      | A plan ready to apply has no **BLOCKED** entries.                                                           |

If **Run workflow** is missing, check that you have write access, Actions is enabled, and the deploy workflow on the default branch has a manual trigger. See the [GitHub manual workflow documentation](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).

### 3. Apply on the same commit

Run **Deploy to Cloudflare** again with `release_action=apply`. Keep the same source commit, `operation`, and `deploy_mode`. Copy the two values from the Plan summary.

- Use **Plan run ID** for `plan_run`.
- Use the full **Plan SHA-256** for `plan_hash`.

Generate and review a new plan if the branch moves to another commit. After Apply succeeds, open the status page from its summary and check that the data timestamp advances. Continue using `/admin` or your existing custom admin path.

## What to expect during a legacy upgrade

For a supported `0014 → 0025` upgrade, the workflow saves the current public homepage snapshot and records a D1 recovery point before pausing probes and admin writes. During maintenance the homepage shows a notice, the last published data, and its original timestamp. After the migrations, Apply switches to the new Worker, updates the frontend as needed, and checks that new public data is published.

In the isolated Dev Cloudflare rehearsal after the snapshot fix, sampled Pages homepage requests returned HTTP 200 during about 29 seconds of maintenance. The rehearsal used the `free` runtime profile on a Paid account. Maintenance duration varies with database size and Cloudflare version propagation. Native Free account limits and a live fork’s GitHub web Sync path still need direct verification.

## If Plan is blocked or Apply stops

| What you see                                                              | What to do first                                                                                                                                                                  |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Plan cannot identify a unique Cloudflare account                          | Verify the account, add `CLOUDFLARE_ACCOUNT_ID` only if needed, and run Plan again.                                                                                               |
| Plan cannot find the existing Worker                                      | Check `UPTIMER_WORKER_NAME` and the account. If a first install created D1 before deploying a Worker, verify the database UUID, set `UPTIMER_D1_ID`, and use `upgrade` to resume. |
| Plan reports a mismatched target, unexpected migration, or profile change | Keep the current site running, review the summary, and correct the relevant setting before planning again.                                                                        |
| Apply entered maintenance or finished only part of the deployment         | Read the failed run’s summary and receipt, then rerun **the original Apply**. Receipts from later attempts include the attempt number.                                            |
| Worker deployed and Pages or final verification failed                    | Use the receipt to check which stages have finished, then retry against the reviewed target. Keep the existing D1 and Worker.                                                     |

Plan artifacts are retained for 30 days. A D1 restore is a separate operation that affects writes made after the recovery point. Prefer resuming the original run when recovering an interrupted upgrade. See [upgrade and recovery](upgrade-and-recovery.md).

## First installation

Fork the repository and enable workflows in **Actions**. Add `CLOUDFLARE_API_TOKEN` and a newly generated `UPTIMER_ADMIN_TOKEN` to your fork. Follow the [GitHub Actions deployment guide](deploy-github-actions.md), choosing `operation=install` for both Plan and Apply. After verification, open the site from the Apply summary and sign in with your admin key to add monitors.
