# Uptimer v0.2.0 部署与升级指南

[English](v0.2.0-upgrade.md) | 中文

**已有站点的升级顺序是同步 fork、运行 Plan、核对目标、手动运行 Apply。** Sync fork 更新 GitHub 上的代码。启用了 Actions 的 fork 同步后应运行 CI，Cloudflare 部署由你在 **Deploy to Cloudflare** 发起。受支持的旧实例由 Action 在原 D1 上迁移并恢复探测。

如果希望 Agent 协助核对配置和执行升级，可以复制 [README 中的升级提示词](../README.zh-CN.md#让-agent-协助升级到-v020)。

## v0.2.0 带来了什么

- **探测历史与资源用量。** D1 按时间桶保存完整的探测样本，并缓冲当前小时的写入。升级会迁移旧样本，同时保留现有 D1 的 UUID。
- **状态页更快看到数据。** 首页优先展示预载数据，再检查更新。延迟图按需加载，尊重系统的减少动态效果设置。图表脚本加载失败时，状态页主体仍可用。
- **公开范围与后台体验。** 监控的公开范围会应用到历史、事件和维护记录。仅关联监控的事件在关联被移除后仍保持相应的可见性限制。后台也改进了同源登录、窄屏对话框和键盘操作。
- **部署可以先审阅，再执行。** Plan 构建并记录目标资源和迁移。Apply 使用同一份已审阅的构建。升级中断后可以继续原 Apply，已提交的迁移会被跳过。

## 选择你的部署方式

| 你的现状                        | 应该怎么做                                                                   |
| ------------------------------- | ---------------------------------------------------------------------------- |
| 还没有部署站点                  | 用 **`install`**。配置两个 Secrets 后，Action 会创建首装所需的资源。         |
| 已有站点，准备升级              | 用 **`upgrade`**。沿用现有 Worker、D1、托管方式与运行配置。                  |
| 原 Apply 已进入维护或迁移后中断 | 在 GitHub 中**重跑原 Apply**，沿用原 Plan。Action 会按 D1 的已提交记录继续。 |
| 已同步 fork，线上还是旧版       | 直接从 **Plan** 开始。                                                       |
| 目标版本已成功部署，站点正常    | 无需再次运行 Apply。                                                         |

默认托管方式是 **Workers + Pages**。已有 **Workers Assets** 单 Worker 站点请选择 `single_worker`。运行配置独立于托管方式，`UPTIMER_RUNTIME_PROFILE` 留空即使用 `free`。已在使用 `paid` 的站点保留 `UPTIMER_RUNTIME_PROFILE=paid`。本次升级沿用原配置，托管迁移和运行模式切换各有独立步骤。详见[配置参考](configuration-reference.zh-CN.md)和[切换说明](upgrade-and-recovery.md#runtimehosting-switches--执行路径与托管切换)。

## 升级已有 fork

### 1. 核对并同步代码

1. 查看上游发布说明，确认你要升级的版本或候选版本已经发布，并已进入你要同步的上游分支。用同一个版本的指南和工作流。
2. 打开自己的 fork，确认目标分支，并检查是否有自定义工作流、Pages Git 集成或其他 push 部署入口。若同步会触发这些入口，先通过 PR 审阅、处理和验证对应配置。
3. 在 fork 首页点 **Sync fork → Update branch**。有冲突时，按 GitHub 提示用 PR 合并，并保留自己的配置。确认 fork 已启用 Actions，等待目标提交的 CI 通过。

普通 fork 一般只需沿用已有的 `CLOUDFLARE_API_TOKEN` 和 `UPTIMER_ADMIN_TOKEN`。已有站点的 `UPTIMER_ADMIN_TOKEN` 应和当前后台密钥一致。确认自定义资源名称和域名仍对应原站点。Plan 会尝试识别唯一的 Cloudflare 账户，并从线上 Worker 的 `DB` 绑定读取 D1 UUID。

[Uptimer 发布页](https://github.com/VrianCao/Uptimer/releases) · [GitHub 同步 fork 文档](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/syncing-a-fork) · [Secrets 与配置](deploy-github-actions.zh-CN.md#1-配置两个-secrets)

### 2. 生成并核对 Plan

进入 fork 的 **Actions → Deploy to Cloudflare → Run workflow**，选定刚核对的分支，选择 `release_action=plan` 和 `operation=upgrade`。托管方式沿用原配置，已有仓库变量时可用 `deploy_mode=auto`。

Plan 成功后打开 **Summary**，按下表核对。

| 核对什么 | 要看到什么                                                                      |
| -------- | ------------------------------------------------------------------------------- |
| 源码     | 指向你要部署的提交。                                                            |
| 目标     | Cloudflare 账户、Worker、D1 UUID 和 Pages 项目（如有）与原站点一致。            |
| 配置     | 托管方式和运行配置与原站点一致。                                                |
| 迁移     | 受支持的 `0014` 旧库会列出待迁移文件并提示维护。没有待执行迁移时会显示 `none`。 |
| 阻塞     | 可以继续 Apply 的计划没有 **BLOCKED** 项。                                      |

如果 **Run workflow** 按钮缺失，检查拥有仓库写权限、Actions 已启用，且默认分支上的部署工作流包含手动入口。详见 [GitHub 手动运行工作流文档](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)。

### 3. 在同一提交运行 Apply

在同一个 **Deploy to Cloudflare** 工作流再次运行，选择 `release_action=apply`。保留相同的分支提交、`operation` 和 `deploy_mode`，填入上一份 Plan 摘要里的两个值。

- `plan_run` 填 **Plan run ID**。
- `plan_hash` 填完整的 **Plan SHA-256**。

分支更新到新提交时，重新生成并审阅 Plan。Apply 完成后，用摘要中的链接打开状态页，确认更新时间再次前进。后台仍通过 `/admin` 或你已配置的自定义路径进入。

## 旧库维护期间会发生什么

对受支持的 `0014 → 0025` 升级，Action 会先保存当前公开首页快照并记录 D1 恢复点，再暂停探测和后台写入。在维护期间，首页显示维护提示、最后一次公开数据和它的原更新时间。迁移完成后，Action 切换新版 Worker，按托管方式更新前端，并检查公开数据重新发布。

Dev 的隔离 Cloudflare 演练中，修复后的完整升级在 Pages 入口观测到约 29 秒的维护窗口，采样的首页请求均为 HTTP 200。该演练使用 Paid 账户上的 `free` 配置。实际维护时长取决于数据库规模和 Cloudflare 版本传播。真实 Free 账户额度及真实 fork 的网页 Sync 路径仍待直接验证。

## Plan 阻塞或 Apply 中断

| 你看到什么                            | 先做什么                                                                                                                                      |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Plan 找不到唯一 Cloudflare 账户       | 核对账户，仅在需要时添加仓库变量 `CLOUDFLARE_ACCOUNT_ID`，再生成 Plan。                                                                       |
| Plan 找不到已有 Worker                | 核对 `UPTIMER_WORKER_NAME` 和目标账户。若是首装时已经创建 D1、Worker 尚未部署，核对已创建的 D1 UUID 后设 `UPTIMER_D1_ID`，用 `upgrade` 续跑。 |
| Plan 报告目标不符、未知迁移或模式变化 | 保持原站点在线，核对摘要并修正相应配置，再生成 Plan。                                                                                         |
| Apply 已进入维护或只完成了一部分      | 查看失败运行的 Summary 和回执，在 GitHub 上重跑**原 Apply**。第二次起的回执文件名带有尝试编号。                                               |
| Worker 已更新，Pages 或最后验收失败   | 从原 Apply 的回执核对已完成阶段，在相同目标上重试。保留现有 D1 和 Worker。                                                                    |

Plan 产物保留 30 天。D1 恢复是独立操作，会影响恢复点之后的写入。升级后需要恢复时，优先让原流程继续，或按已审阅的恢复方案处理。详见[升级与恢复](upgrade-and-recovery.md)。

## 首次部署

Fork 后在 **Actions** 中启用工作流。为自己的 fork 配置 `CLOUDFLARE_API_TOKEN` 和新生成的 `UPTIMER_ADMIN_TOKEN`。按照 [GitHub Actions 部署指南](deploy-github-actions.zh-CN.md)操作，在 **Plan** 和 **Apply** 都选择 `operation=install`。部署成功后从 Apply 摘要打开站点，用设置的管理密钥登录后台并添加监控。
